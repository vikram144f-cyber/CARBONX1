# CARBONX — Data Sources Reference

**Version:** 1.0  
**Status:** Architecture-approved  
**Updated:** 2026-08-22

This document answers the question **"Where does this data actually come from?"** for every feature in CARBONX. It is the authoritative reference for data source decisions. No production feature may rely on a data origin not documented here.

---

## 1. Data Origin Classification

Every value in CARBONX belongs to exactly one of these origin classes:

| Class | Code | Meaning |
|---|---|---|
| Real external public data | `EXTERNAL` | Ingested from a public or third-party API/dataset |
| Real organization data | `ORG_DATA` | Entered or imported by the user's organization; stored in PostgreSQL |
| Deterministic calculation | `CALC` | Computed by the backend engine from real inputs; reproducible |
| AI interpretation | `AI` | Generated by an LLM from structured inputs; narrative only |
| Controlled historical replay | `REPLAY` | Real historical data re-run through the genuine backend pipeline |
| Simulated / demo scaffold | `DEMO` | Placeholder data used only in initial seed; clearly marked |

The distinction between these classes is **enforced in every data record** via the `createdByType` provenance field. See Section 7.

## 2. Environmental Event Data — NASA FIRMS (Primary)

### 2.1 What it is

NASA FIRMS (Fire Information for Resource Management System) provides near-real-time and historical **satellite fire and thermal anomaly detections** from multiple instruments.

CARBONX uses FIRMS as its **primary environmental event source**. This is the layer that triggers the entire incident detection pipeline.

### 2.2 Instruments supported

| Instrument | Satellite | Resolution | Typical latency | Notes |
|---|---|---|---|---|
| VIIRS (Suomi NPP) | Suomi NPP | ~375m | ~3h from overpass | Higher resolution; preferred for P0 |
| VIIRS (NOAA-20) | NOAA-20 | ~375m | ~3h from overpass | Near-duplicate coverage; good for corroboration |
| MODIS (Terra/Aqua) | Terra, Aqua | ~1km | ~3h from overpass | Lower resolution; longer historical archive |

### 2.3 What CARBONX receives

Each FIRMS record provides:

| Field | Meaning | Used by CARBONX |
|---|---|---|
| `latitude` | Detection centroid latitude | Stored as event geometry Point |
| `longitude` | Detection centroid longitude | Stored as event geometry Point |
| `acq_date` | Acquisition date (UTC) | `observedAt` |
| `acq_time` | Acquisition time (HHMM UTC) | Combined with `acq_date` for `observedAt` |
| `satellite` | Satellite identifier (e.g., N, T, A) | Stored in `sourceMetadata` |
| `instrument` | Instrument name (VIIRS, MODIS) | Stored in `sourceMetadata` |
| `confidence` | Detection confidence (n/l/h for VIIRS; 0–100% for MODIS) | Mapped to `sourceConfidence` (0–1) |
| `frp` | Fire Radiative Power (MW) | Stored in `sourceMetadata`; informs severity |
| `bright_t31` / `bright_ti4` | Brightness temperatures | Stored in `rawPayload`; not exposed directly |
| `version` | NRT/Standard product version | Stored in `sourceMetadata` |

### 2.4 How it is accessed

**Primary method: FIRMS Area API**

```
GET https://firms.modaps.eosdis.nasa.gov/api/area/{format}/{MAP_KEY}/{source}/{bbox}/{days}
```

- `format`: `csv` or `json`
- `MAP_KEY`: Server-side environment variable `NASA_FIRMS_MAP_KEY`
- `source`: `VIIRS_SNPP_NRT`, `VIIRS_NOAA20_NRT`, `MODIS_NRT`, or archive equivalents
- `bbox`: Bounding box derived from all monitored project centroid/boundary extents
- `days`: Configurable lookback window (1–10 for NRT; archive API for older data)

**Authentication:** Free registration at [firms.modaps.eosdis.nasa.gov](https://firms.modaps.eosdis.nasa.gov/api/). Returns a MAP_KEY. No OAuth required.

**API key rule:** `NASA_FIRMS_MAP_KEY` is a server-side environment variable. It never appears in a client bundle or `NEXT_PUBLIC_` variable.

**Alternative: FIRMS archive API** for historical data replay scenarios:
```
GET https://firms.modaps.eosdis.nasa.gov/api/area/{format}/{MAP_KEY}/{source}/{bbox}/{range}/{date}
```

### 2.5 Critical distinction — what a FIRMS hotspot means

> **A NASA FIRMS hotspot is a satellite observation that a thermal anomaly consistent with fire was detected at a specific geographic point and time.**

It is NOT:
- Proof that an entire carbon project is destroyed
- A measurement of burned area
- A ground-truth confirmation of fire
- A direct measurement of credit invalidation

CARBONX must communicate this distinction explicitly in every assessment.

The `EvidenceLabel` on a FIRMS-derived `EvidenceRecord` is always `ESTIMATED` when used as the basis for an impact area calculation (because the point is buffered to estimate area), and `OBSERVED` only for the raw detection point itself.

### 2.6 Ingestion service

See `FIRMSIngestionService` in `lib/services/firms-ingestion.ts`. Full pipeline defined in `docs/data-pipeline.md`.

## 3. Environmental Event Data — Satellite Imagery (Secondary / P1)

### 3.1 Context

NASA FIRMS provides **point detections**. Satellite imagery can provide **visual evidence** of burned areas, deforestation, and land change. However, raw satellite imagery processing (downloading GeoTIFF tiles, computing spectral indices, analyzing change) is complex and is **not required for the P0 workflow**.

CARBONX's P0 workflow works entirely with FIRMS point detections buffered into estimated impact zones.

### 3.2 Evaluated sources

#### Microsoft Planetary Computer (STAC API)

| Property | Value |
|---|---|
| Data types | Sentinel-2 L2A (10m optical), Landsat Collection 2 (30m optical) |
| Access | Free; API key required (Azure subscription or anonymous read for public collections) |
| Authentication | API key or anonymous for read |
| What CARBONX gets | Cloud-hosted COG (Cloud-Optimized GeoTIFF) tiles queryable by bbox + date range |
| Practicality | Moderate — STAC query is straightforward; downloading/processing tiles requires compute |
| Workflow role | Visual evidence overlay; NDVI change computation |
| Evidence type | OBSERVED (imagery) |
| Priority | **P1** — useful for visual evidence panels; not required for risk calculation |

#### Copernicus Data Space Ecosystem (ESA)

| Property | Value |
|---|---|
| Data types | Sentinel-2 L2A, Sentinel-1 SAR |
| Access | Free; registration required; OData/STAC API |
| Authentication | OAuth2 with registered credentials |
| What CARBONX gets | GeoTIFF scenes; requires clipping to AOI |
| Practicality | Lower — Sentinel Hub (paid service built on top) is more practical |
| Priority | **P2** — requires more infrastructure than P1 alternatives |

#### Sentinel Hub (Sinergise / Planet)

| Property | Value |
|---|---|
| Data types | Sentinel-2, Landsat, MODIS pre-processed; NDVI, NBR, EVI via Evalscript |
| Access | Paid; free trial available |
| Authentication | OAuth2 client credentials |
| What CARBONX gets | Pre-computed index images (NDVI, dNBR) over specified bbox + date range |
| Practicality | High — single API call returns a processed image |
| Priority | **P1 stretch** — practical but has cost; useful for a polished demo |

### 3.3 CARBONX position on satellite imagery (P0)

> **P0 does not integrate satellite imagery processing.** The core risk calculation uses FIRMS detections + project boundary GeoJSON + Turf.js geometry. Adding satellite imagery would require: tile download, projection, clipping, index computation, and change detection — none of which is required for a working end-to-end pipeline.

When satellite imagery is added (P1+), it appears as an additional `EvidenceRecord` linked to the incident with:
- `label: OBSERVED`
- `sourceConfidence`: derived from image cloud cover and resolution
- `sourceMetadata`: instrument, acquisition date, band indices used

The `docs/data-pipeline.md` marks satellite imagery as an optional parallel evidence branch.

## 4. Carbon Project Data

### 4.1 Classification

Carbon project data has three distinct sub-types with different sources:

| Sub-type | Source | Access |
|---|---|---|
| Project identity and metadata | Public carbon registries | Public web / partial API |
| Project geographic boundary | Registry documents or user-provided | Manual import or partial public files |
| Credit holdings (what the org owns) | Organization-private | User-entered or CSV import |

### 4.2 Public project metadata sources

#### Verra Registry (VCS / REDD+)

- **URL:** https://registry.verra.org/
- **API:** `https://registry.verra.org/app/search/VCS` (JSON search endpoint; unofficial, scraping-adjacent)
- **What is available:** Project name, ID, methodology, country, proponent, issuance totals, project documents
- **What is NOT available:** GeoJSON boundaries via API. Project area KML/shapefiles are sometimes attached to project documents (PDFs) but are not systematically accessible via API.
- **CARBONX use:** Seed data for `CarbonProject.registryId`, `projectName`, `methodology`, `countryCode`

#### Gold Standard Registry

- **URL:** https://registry.goldstandard.org/
- **API:** Limited public JSON endpoint
- **Boundary availability:** Generally not available via API

#### American Carbon Registry (ACR)

- **URL:** https://americancarbonregistry.org/
- **Boundary availability:** Not available via API

#### Global Forest Watch / Carbon Mapper

- **URL:** https://globalforestwatch.org/
- **What is available:** Some REDD+ project boundaries as shapefiles; downloadable for certain well-documented projects
- **Priority:** P1 — useful source for specific well-known projects

### 4.3 Project boundary strategy (GeoJSON)

> **No public carbon registry exposes complete, structured, downloadable GeoJSON for all projects via a stable API.** Boundaries are published inconsistently across registry documents, shapefiles, and KML files. CARBONX must therefore support manual GeoJSON import as its primary boundary mechanism.

**P0 strategy:**

1. **Seed data:** For the demo/initial seed, CARBONX pre-seeds 2–3 real, well-documented carbon projects where public shapefiles or GeoJSON are available (e.g., projects listed on Global Forest Watch with downloadable boundaries).
2. **Import endpoint:** `POST /api/projects/[id]/boundary` accepts a valid GeoJSON Feature or FeatureCollection. Developer A validates it with Turf.js.
3. **Provenance:** Every imported boundary records `boundarySource`, `boundarySourceUrl`, `boundaryConfidence`, and `lastVerifiedAt`.

**P1 strategy:**
- Registry document parser (extract KML → convert to GeoJSON)
- Global Forest Watch integration for listed projects

**Boundary data model fields:**

```
ProjectBoundary:
  projectId
  version           (integer, incrementing)
  geojson           (validated GeoJSON Feature/FeatureCollection)
  areaHa            (pre-computed from Turf.js at import time)
  boundarySource    (e.g., "user-import", "global-forest-watch", "verra-document-kml")
  boundarySourceUrl (original file URL if available)
  boundaryConfidence (HIGH / MEDIUM / LOW / UNKNOWN)
  acquiredAt
  verifiedAt
  isCurrent         (boolean)
  createdById       (userId or "system")
```

### 4.4 Credit holdings — organization-private data

Credit holdings (what a specific organization actually owns) are not publicly discoverable. They are:

- Entered manually via the CARBONX UI
- Or imported via a structured CSV upload

**CreditLot data model:**

```
CreditLot:
  projectId           (FK → CarbonProject)
  portfolioId         (FK → Portfolio)
  registrySerialRef   (optional; registry issuance reference)
  vintage             (year the credits were issued)
  heldQuantity        (number of credits currently held)
  acquiredQuantity    (number acquired at time of purchase)
  refValuePerUnit     (reference price at acquisition)
  refCurrency         (ISO 4217; e.g., "USD")
  valuationBasis      ("market" | "book" | "user-provided")
  acquisitionDate
  status              (ACTIVE | RETIRED | CANCELLED | TRANSFERRED)
  notes
  importedAt
  importedByUserId
```

> **Financial exposure calculations query these database values.** No credit quantity or reference price is hardcoded in the frontend.

## 5. Geospatial Data

### 5.1 Project boundaries

Source: PostgreSQL (`ProjectBoundary.geojson`). Stored as validated WGS84 GeoJSON. Retrieved by the Service Layer — never raw-queried from the frontend.

### 5.2 Event geometries

Source: Normalized from NASA FIRMS (lat/lng → GeoJSON Point). Stored in `EnvironmentalEvent.geometry`.

### 5.3 Impact zone geometry

Source: Deterministically computed by `lib/services/geospatial.ts` using Turf.js. A FIRMS point detection is buffered using a configurable radius (`FIRMS_POINT_BUFFER_KM`, default 1km) to produce an estimated impact circle. The result is stored in the `EvidenceRecord` and labeled `ESTIMATED`.

> This estimated circle is **not** a scientifically measured burned area. It is a conservative spatial proxy for geospatial intersection purposes.

### 5.4 Intersection result

Source: `turf.intersect(projectBoundaryPolygon, eventBufferPolygon)` — deterministic calculation. The intersection polygon (if any) is used to compute `estimatedImpactHa` and `impactPct`. These are labeled `CALC` in provenance.

### 5.5 2D map tiles (basemap)

Source: OpenStreetMap tiles (via Leaflet's default tile provider) — free, no API key required. Alternatively, Mapbox tiles via `NEXT_PUBLIC_MAPBOX_TOKEN` for higher-quality basemaps (optional; requires Mapbox account).

## 7. Data Provenance Model

Every `EnvironmentalEvent`, `EvidenceRecord`, and `RiskAssessment` carries a provenance block answering **"Where did this value come from?"**

### 7.1 createdByType enum

```
EXTERNAL_SOURCE    — data arrived from an external API or dataset
SYSTEM_CALCULATION — produced by a deterministic backend algorithm
AI_GENERATION      — produced by an LLM from structured inputs
HUMAN_ACTION       — recorded as a result of a human decision or input
REPLAY             — real historical data re-run through the pipeline
```

### 7.2 Provenance fields (applied to EnvironmentalEvent)

```
sourceName        (e.g., "NASA FIRMS VIIRS NRT")
sourceId          (e.g., FIRMS unique identifier or content hash)
sourceUrl         (e.g., the API endpoint that returned this record)
sourceInstrument  (e.g., "VIIRS_SNPP")
observedAt        (when the satellite detected it — from FIRMS acq_date + acq_time)
acquiredAt        (when CARBONX ingested it)
originType        (OBSERVED | REPLAYED | MODELED | USER_REPORTED)
dataVersion       (FIRMS product version)
ingestorVersion   (FIRMSIngestionService version string)
rawPayload        (full original record stored for audit purposes)
createdByType     (EXTERNAL_SOURCE for live; REPLAY for historical replay)
```

### 7.3 Provenance fields (applied to RiskAssessment)

```
engineVersion       (e.g., "geospatial-v1.0")
methodologyVersion  (e.g., "risk-v1.0")
boundaryId          (which ProjectBoundary version was used)
inputEvidenceIds[]  (which EvidenceRecords were inputs)
assumptions         (JSON of documented assumptions, e.g., buffer radius used)
createdByType       (SYSTEM_CALCULATION)
supersededById      (null if current; set if a newer assessment was created)
```

## 8. AI Data

### 8.1 Source

Google Gemini 1.5 Flash (default) or OpenAI GPT-4o (configurable via `AI_PROVIDER` env var).

### 8.2 What CARBONX sends to the LLM

A structured JSON payload built entirely from the `RiskAssessment` database record. The LLM never receives raw satellite data, is never asked to calculate geometry, and is never asked to determine if credits are valid.

The payload schema is versioned (`ai-input-v1.0`) and validated with Zod before transmission.

### 8.3 What CARBONX receives from the LLM

A structured JSON response (`ai-output-v1.0`) validated with Zod. Contains five narrative sections:

- `facts` — what the evidence record shows
- `estimatedImpacts` — what this may mean
- `uncertainties` — explicit limitations and caveats
- `portfolioConsequences` — potential implications for credit holdings
- `recommendations` — suggested next steps

**AI output is labeled `AI` in provenance and is never the source of numeric values.**

### 8.4 Failure behavior

If the AI API is unavailable or the response fails schema validation, `AIReport` is set to null. The incident workflow continues without interruption. The UI renders "Interpretation Unavailable."

## 9. Blockchain Data

### 9.1 What is anchored

The blockchain receives a **cryptographic hash of a canonical evidence package**. It stores no application state.

### 9.2 What CARBONX stores on-chain

A single `EvidenceAnchored` event emission containing:
- `incidentId` (bytes32)
- `evidenceHash` (bytes32 — keccak256 of canonical JSON)
- `eventType` (string)
- `block.timestamp`

### 9.3 What CARBONX stores in PostgreSQL from the anchor

- `txHash` — the Ethereum transaction hash
- `blockNumber`
- `network` (e.g., "sepolia")
- `contractAddress`
- `status` (PENDING / SUBMITTED / CONFIRMED / FAILED)
- `canonicalJson` — the exact JSON that was hashed (for independent verification)
- `hash` — the keccak256 hash

### 9.4 Testnet

Sepolia testnet. RPC via Alchemy or Infura (`BLOCKCHAIN_RPC_URL`). Contract pre-deployed; address in `BLOCKCHAIN_CONTRACT_ADDRESS`.

> **No fake transaction hashes are generated.** If the blockchain is unavailable, the anchor status is PENDING or FAILED, and the CARBONX workflow continues unaffected.

## 10. Controlled Historical Replay

CARBONX supports replaying real historical environmental events through the genuine backend pipeline for demonstration and testing purposes.

### 10.1 What replay means

A real NASA FIRMS observation from a past date (e.g., a documented California wildfire from 2023) is stored in the database (seeded by Developer A). When a user triggers "Run Historical Scenario," the system:

1. Reads the stored historical `EnvironmentalEvent` from the database
2. Passes it through the real ingestion → geospatial → risk → AI → blockchain pipeline
3. Creates real `Incident`, `RiskAssessment`, `AIReport`, and `BlockchainAnchor` records
4. Presents real backend results to the frontend

### 10.2 What replay is NOT

- Not a `setTimeout` fake state change
- Not a hardcoded "detected" flag
- Not a frontend-only simulation
- Not a pre-baked static response

### 10.3 Provenance for replay

Replayed events set `originType: REPLAYED` on the `EnvironmentalEvent` record. This is displayed in the UI so users and judges can see that it is a replay, not a live detection.

## 11. Continuous Monitoring

### 11.1 Mechanism

A scheduled ingestion job (`FIRMSIngestionService.scheduled()`) runs at a configurable interval (default: every 6 hours).

### 11.2 Cursor-based deduplication

The job records the last successful ingestion timestamp in a `MonitoringCheckpoint` database table. On each run, it fetches FIRMS observations since that checkpoint. After successful persistence, the checkpoint is advanced.

### 11.3 Deduplication strategy

1. Primary: `sourceId` match (FIRMS record identifier if available)
2. Fallback: Content hash of `(sourceName, latitude, longitude, acq_date, acq_time)` — if identical, the record is a duplicate and is skipped

### 11.4 Failure handling

If a scheduled run fails: the checkpoint is not advanced, so the next run re-fetches from the last successful point. Alert logged to observability layer. Max 3 consecutive failures before an operator alert is raised.

## 12. 3D Investigation — Data Contract

The Interactive Mode (R3F/3D scene) derives all visual states from real backend data. It never invents or hardcodes visual state.

### 12.1 ProjectVisualState contract

The backend exposes a `GET /api/projects/visual-states` endpoint returning:

```typescript
interface ProjectVisualState {
  projectId: string;
  projectName: string;
  centroidLng: number;
  centroidLat: number;
  status: "MONITORING" | "EVENT_DETECTED" | "UNDER_ASSESSMENT" |
          "AUDIT_RECOMMENDED" | "AUDIT_IN_PROGRESS" | "RESOLVED";
  integrityRisk: "LOW" | "MEDIUM" | "HIGH" | "CRITICAL" | null;
  evidenceConfidence: "LOW" | "MEDIUM" | "HIGH" | null;
  activeIncidentId: string | null;
  affectedAreaEstimateHa: number | null;
  lastUpdatedAt: string;
}
```

### 12.2 Visual state mapping (artistic — not scientific)

| Backend state | 3D visual representation |
|---|---|
| MONITORING | Healthy green environment, no anomalies |
| EVENT_DETECTED | Smoke/heat shimmer particle effect at event coordinates |
| UNDER_ASSESSMENT | Pulsing amber boundary outline |
| AUDIT_RECOMMENDED | Red boundary with evidence hotspot markers |
| AUDIT_IN_PROGRESS | Investigation overlay with evidence markers |
| RESOLVED | Muted grey state |

> The 3D terrain is **artistic and stylized**. It is not a scientifically accurate digital elevation model unless terrain data (e.g., Mapbox Terrain, Cesium terrain tiles) is explicitly integrated (P2).

## 14. What Remains Simulated or Absent in P0

The following items are **explicitly not real data** in P0, and are marked accordingly:
